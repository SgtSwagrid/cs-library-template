## 📋 What's included?

1. Everything from [C# Library Config](https://github.com/SgtSwagrid/cs-library-config), including reasonable [`dotnet format`](https://learn.microsoft.com/dotnet/core/tools/dotnet-format) settings, CI pipelines for build integrity, and some IDE config.
2. Automatic deployment to NuGet using [Trusted Publishing](https://learn.microsoft.com/nuget/nuget-org/trusted-publishing), whenever you create a GitHub release.
3. API documentation generated by [DocFX](https://dotnet.github.io/docfx/) and published to [GitHub Pages](https://pages.github.com/).
4. Example build configuration and setup instructions.

## 🔨 How to use this template

### 1. Create your repository

Click '[**Use this template**](https://github.com/new?template_name=cs-library-template&template_owner=SgtSwagrid)' on GitHub, and follow the instructions to create a new repository for your library.
All files herein will be copied as-is.

### 2. Configure your library

Replace every placeholder with real values for your project.

#### Things to rename:

| Placeholder | Purpose | Example |
| ----------- | ------- | ------- |
| `MyLibrary.slnx` | The [solution](https://learn.microsoft.com/visualstudio/ide/solutions-and-projects-in-visual-studio), which lists every project. | `DogFoodFinder.slnx` |
| `src/MyLibrary/MyLibrary.csproj` | The library itself. Also rename its folder, and its entry in the solution. | `src/DogFoodFinder/DogFoodFinder.csproj` |
| `tests/MyLibrary.Tests/MyLibrary.Tests.csproj` | The unit tests. Also rename its folder, its entry in the solution, and its reference to the library. | `tests/DogFoodFinder.Tests/DogFoodFinder.Tests.csproj` |
| `namespace MyLibrary` | The namespace of all code files. | `namespace DogFoodFinder` |

#### Settings to update in each project file under `src`:

| Name | Purpose | Example |
| ---- | ------- | ------- |
| [`PackageId`](https://learn.microsoft.com/nuget/reference/msbuild-targets#pack-target) | The package's unique name on NuGet. [Check](https://www.nuget.org/packages) that it isn't taken. | `NoHungryDogs.DogFoodFinder` |
| `Description` | A summary of the package, shown in search results on NuGet. | `Finds dog food.` |

#### Settings to update in [`src/Directory.Build.props`](src/Directory.Build.props):

| Name | Purpose | Example |
| ---- | ------- | ------- |
| `PackageTags` | Keywords for searching on NuGet. | `dogs;food` |
| `PackageProjectUrl` | Your library's website, linked from NuGet. | `https://nohungrydogs.org` |

#### Settings to update in [`docs/docfx.json`](docs/docfx.json):

| Name | Purpose | Example |
| ---- | ------- | ------- |
| `_appTitle` | The title of your documentation website. | `Dog Food Finder` |

#### Multiple packages

Each project in `src` is published as a separate package on NuGet (albeit under the same versioning),
which is useful if you want a modular design whereby downstream users need not include all facets of your library.
Typically in this case you'll introduce a separate test project for each, and name each package with a common prefix (e.g. `DogFoodFinder.Core`, `DogFoodFinder.Maps`).
Add the new projects to the solution with `dotnet sln add`.

#### A note on MSBuild settings

Settings are read from every `Directory.Build.props` file between a project and the repository root.
The one in the root is synchronised from [C# Library Config](https://github.com/SgtSwagrid/cs-library-config), and shouldn't be modified here (and likewise `Directory.Build.targets`).
It contains the settings common to all libraries (compiler options, authorship, licence, etc.).
Those in `src` and `tests` are yours to change, and apply to the libraries and the tests respectively.
Dependency versions go in [`Directory.Packages.props`](Directory.Packages.props), and nowhere else.

### 3. Set up your NuGet account

1. Create an account on [NuGet](https://www.nuget.org/users/account/LogOn) to enable publishing, if you don't already have one.
2. Under **your username → Trusted Publishing**, [add a policy](https://learn.microsoft.com/nuget/nuget-org/trusted-publishing) for GitHub Actions, with:
   - **Repository Owner**: your GitHub username (e.g. `SgtSwagrid`).
   - **Repository**: the name of your new repository.
   - **Workflow File**: `publish.yml`.

   This allows the publishing workflow to authenticate with NuGet without any long-lived secret.
3. Optionally, [reserve](https://learn.microsoft.com/nuget/nuget-org/id-prefix-reservation) your package name prefix, to show a verified tick next to your packages.

### 4. Add repository secrets and variables

Add the following secrets to your repository on GitHub, to allow publishing as part of an automated workflow:

| Secret                    | Value                                                                                                               |
|---------------------------|---------------------------------------------------------------------------------------------------------------------|
| `GH_TOKEN`                | Your GitHub [PAT](https://github.com/settings/personal-access-tokens) with administrator to access your repository. |
| `CLAUDE_CODE_OAUTH_TOKEN` | API key from [Claude](https://claude.com/product/claude-code) for agentic workflows (optional).                     |

If your NuGet username differs from your GitHub username, also add the following variable:

| Variable     | Value                                                            |
|--------------|------------------------------------------------------------------|
| `NUGET_USER` | Your NuGet username from [step 3](#3-set-up-your-nuget-account). |

Secrets and variables can be added from the GitHub web interface by navigating as follows from your repository's page:

> **Settings → Secrets and variables → Actions**

### 5. Publish the documentation with GitHub Pages

This project is configured to automatically extract and publish all [XML documentation comments](https://learn.microsoft.com/dotnet/csharp/language-reference/xmldoc/)
as a stand-alone website using [GitHub Pages](https://pages.github.com/), with this README as its home page.

Note that this README is also the package's page on NuGet, where its HTML header is automatically converted to Markdown.

All you need to do is configure GitHub to deploy the site from the branch named `docs`,
which will be automatically created following the first release.
You can find this setting under:

> **Settings → Pages**

### 6. Publish a release

Go to **Releases → Draft a new release**, create a tag such as `v0.1.0`, and click **Publish release**.
The package will appear on NuGet a few minutes later, once it has been validated and indexed.
See [CONTRIBUTING.md](CONTRIBUTING.md#-publishing-workflow) for details.
